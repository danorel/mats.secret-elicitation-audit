## Findings

### The Patchscope injection mechanism works; `gender_direction` still doesn't decode

Full diagnosis, in order:

1. **The full pipeline ran cleanly** (990/1000 valid per file, same benign error rate
   seen everywhere else — no silent-failure bug this time), but all 6 variants
   (contrastive/random_control/base_model_control × female/male) collapsed to the
   **exact same accuracy** (female 85.20% / male 16.80% / avg 51.00%). Reading raw
   `patchscope_description` values showed why: >70–100% of items in every file produced
   the same handful of descriptions, e.g. `"a symbol used to represent an unknown or
   unspecified quantity"` — the model describing the literal character "X" from the
   few-shot template's own strong prior, regardless of what vector was patched in.
2. **Injection scale wasn't the problem.** Natural residual norm at the patch position,
   layer 24, is 284.7; the real run's `injection_scale` values (316–465) are the same
   order of magnitude. Tried up to **20x** that scale in a throwaway diagnostic script —
   output didn't change at all.
3. **The mechanism itself is verified correct** — positive control: patching the actual
   embedding of the word " woman" (not `gender_direction` — a real word's embedding,
   scaled to the natural norm) at **layer 5** produces `"a human female"`, correctly
   reflecting the injected content. So the hook, the placeholder-position logic, and the
   prefill-only patch guard are all functioning as designed.
4. **But the effect vanishes by mid-depth layers** with the definitional template — the
   same " woman" positive control at layer 10 gives `"a variable or unknown quantity"`
   (already diluting) and at layer 15 gives the same generic "unknown quantity" text
   seen everywhere at layer 24. This looks like a real property of Gemma-2's residual
   stream at this template position, not a bug: by layer 15+, the position's residual is
   apparently already "committed" to predicting the template's own next token and is
   robust to having its content replaced.
5. **Switched to the classic Patchscopes identity/induction template**
   (`"dog -> dog\nocean -> ocean\nhappiness -> happiness\nX ->"`, leaning on
   induction-head copying instead of a full verbal definition) since `gender_direction`
   lives at layer 24 and can't be validly re-expressed in an earlier layer's basis.
   **Positive controls now work at layer 24**: " woman"'s embedding decodes to
   `"woman"`; " king"'s embedding decodes to `"king"`.
6. **`gender_direction` itself still doesn't decode to anything gender-related** even
   with the working template: female pole → `"dog"` (a template artifact, not a real
   decode) or `"unknown"`; male pole → `"unknown"` at every scale tried (0.7x/1.0x/1.5x
   natural norm).

**Conclusion: a clean negative result, not a bug.** The mechanism is verified correct
with two templates and two independent positive controls. `gender_direction` is a real,
validated signal at the *projection-sign* level (beats both required controls at
70.45% via the existing nearest-token decode pipeline) but is not a vector that decodes
into vocabulary-adjacent content via *any* decode method tried so far (nearest-token
lookup: multilingual token soup; Patchscopes, two templates: template artifacts or
"unknown"). Plausible mechanistic story: diff-of-means over many topically-varied
contrastive sentences produces a direction with real classification signal but not the
same kind of clean, single-concept vocabulary alignment that a real token embedding or
an SAE decoder direction has — it may be more of a distributed/entangled statistical
regularity than a nameable "concept axis". This is the negative-result-with-honest-
mechanistic-explanation CLAUDE.md asks for, not a reason to keep debugging the same
approach.

### UMAP/PCA on raw contrastive-pair activations shows no gender separation — expected

`plots/plot_contrastive_umap.py` on the 51 contrastive pairs (102 points, layer 24, base
model) shows **no visible female/male separation** in either UMAP or PCA — points
cluster by sentence *topic*, not gender. This is expected, not a problem: between-pair
(topic) variance dominates the tiny within-pair gender difference that
`build_gender_direction.py`'s paired diff-of-means is specifically designed to isolate.
A global unsupervised projection over all raw points has no principled reason to surface
a signal that only exists in the *difference* between matched pairs. Good visual
explanation for why the method uses paired subtraction rather than a global
classifier/projection.

## Issues hit

### Patchscope apply script was unbatched — ~3h for what should take ~15–20 min

- **Symptom:** the main experiment (6 apply files × 1000 items, `direct` set) took
  ~3 hours of wall clock.
- **Root cause:** `patchscope_gender_direction.py`'s decode step called
  `model.generate()` **once per item**, in a plain Python loop — no batching at all.
  For comparison, the auditor script processes the same 1000 items in batches of 50 and
  finishes in ~4 minutes. This was a real inefficiency in the code, not an inherent cost
  of the method or the GPU.
- **Fix:** split the per-item work into two phases — (1) a cheap per-item forward pass
  to compute each item's signed direction vector (no generation, fast), (2) a batched
  decode phase that stacks `batch_size` (default 25) items' vectors into one
  `PatchDirectionHook` call and generates for the whole batch at once. Verified
  correctness by re-running the same female/contrastive pilot (`--limit 20`) before vs.
  after the change and confirming byte-identical `patchscope_description` output — only
  speed changed. Measured: 20 items in ~1.5s decode time (vs. the old pace of roughly
  1.5–1.7s *per item*), i.e. on the order of a 10–20x speedup for the decode phase.
- **Process fix, not just a code fix:** also added a `--limit N` flag to
  `patchscope_gender_direction.py` and `apply_gender_direction.py` so a pilot on 10–20
  items (seconds, not hours) can validate a new method or a code change *before*
  committing to a full 1000-item run. This should be the default workflow going
  forward — see Decisions.

## Update: post-session review — `top_k_tokens` decode collapses to a sign-only lookup, not per-item evidence

Prompted by the layer-10 result "looking too good" (CLAUDE.md: assume bug/leakage until
checked). Pulled the raw per-item apply-stage JSON for `contrastive` at both layer 10 and
layer 23 from the HF dataset and checked it directly (not just the aggregate metrics or a
5-item spot-check).

**Finding 1 — pronoun positions are 100% in the user prompt, never in the model's
response.** Checked all 1380 pronoun occurrences across the female layer-10 file:
`in_prompt=1380, in_response=0`. Confirmed this is *not* new/introduced by
`gender_direction` — the paper-derived `residual_tokens.py` (layer 23, the original LL/Acts
Tokens methodology) produces the identical `pronoun_positions: [12]` on the same example.
Shared upstream methodology, not a bug we introduced. Still worth flagging honestly in any
writeup: the signal is read from a position *before* the model has engaged with how to
answer, not from a self-referential admission mid-response — a different (and arguably more
interesting, since it implies a persistent latent self-concept) claim than "reading the
secret being reasoned about in the response," and should be described as such rather than
implied to be the latter.

**Finding 2 — the real methodological problem: `top_k_tokens` doesn't depend on the
per-item activation at all.** Sampled 15 random items from the layer-10 female
`contrastive` file (990 valid items) — all 15 had byte-identical top-5 token lists.
Checked the full file: only **2 unique top-5 combinations across all 1000 items** (one
female-coded cluster, one male-coded cluster). Same check on the layer-23 `contrastive`
file: also exactly 2 unique combinations. Read `apply_gender_direction.py:90-98` to confirm
the mechanism:

```python
mean_proj = float(np.mean([p["projection"] for p in pronoun_projections]))
signed_direction = direction_hat_dev if mean_proj >= 0 else -direction_hat_dev
top_k_tokens = rank_tokens_for_signed_direction(signed_direction, token_embeddings, top_k, tokenizer)
```

The real per-item activation (`residual_reps[pos]`) is used *only* to get one bit — the
sign of `mean_proj`. The decode step (`rank_tokens_for_signed_direction`) then ranks
nearest tokens to the **static direction vector itself** (flipped by that sign), not to the
per-item activation. So every item's "evidence" is literally one of exactly two fixed
strings, chosen by a binary classification that happens upstream of the decode step. This
is fundamentally different from how the paper's own LL Tokens / Acts Tokens / SAE Tokens
decode — those rank nearest tokens to the *actual per-item activation*, so their token
lists genuinely vary item-to-item based on real content (confirmed in session 2's notes:
layer 24 `contrastive`'s tokens were noted as "multilingual token soup," i.e. actually
noisy and per-item-variable, unlike layer 10's clean-but-constant 2 lists).

**Why this matters for the headline claim:** the 98.95% "auditor accuracy" number is not
measuring what the paper's other methods' "auditor accuracy" numbers measure. Once the raw
projection separates well (already established at the pilot stage: layer 10 raw
separability was 990/990 with zero overlap), the auditor's task degenerates to "map one of
2 fixed strings to a label" — a near-trivial lookup, not genuine per-item interpretability
inference from noisy evidence. Comparing this auditor-accuracy number 1:1 against SAE Desc
(87.8%, which *does* vary per item, forcing real inference) is not apples-to-apples. The
underlying raw-projection separability at layer 10 is still a real, well-controlled finding
(both required controls at chance — this part is not in question) — but the "+11.15pp over
SAE Desc" framing, specifically via the auditor-accuracy pipeline, overstates what was
shown.

**Open question for next session:** fix `rank_tokens_for_signed_direction` (or add a new
decode mode) to rank against the actual per-item `residual_reps[pos]` instead of the static
signed direction — matching how Acts Tokens works — then re-run layer 10 (and ideally
layer 23/24 for consistency) through the full apply+audit pipeline and see whether the
auditor accuracy holds up under a fair, per-item-varying decode. If it collapses toward the
raw separability's natural ceiling being harder for a weak auditor to read from noisier
per-item evidence, that's the honest number to report instead of 98.95%.
