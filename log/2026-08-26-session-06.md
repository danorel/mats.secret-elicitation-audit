## Findings

### The write-up's headline attribution is not supported by the code — the contrastive direction contributes nothing to the decoded evidence

In `process_pair()` (`elicitation_methods/gender_direction.py:210`), when `candidate_size`
is `None` — confirmed as the actual config for the headline `final/gender_direction`
run via its `evidence.json` metadata (`"candidate_size": null`) — the decode step computes
`residual_similarities` from `residual_reps` (the raw per-item residual at pronoun
positions) and `token_embeddings` only. `direction_hat` is never referenced in that
computation. It appears exactly once elsewhere in the function, in the diagnostic
`mean_projection` field — and `prompts/gender/auditor_guess_tokens.txt` fills only
`{top_tokens}`, never `mean_projection`, confirmed by reading the template directly.

**Consequence:** for the headline run, the contrastive direction's only real contribution
to the 68.55% result is upstream — selecting *which layer and which token positions to
read* (via the two full-scale sweeps built in session 4: rank sweep and sign-separability
sweep). The decode itself is mathematically identical in form to Acts Tokens' own
readout, just applied at a different layer/position. This is not "verified item-by-item
on a sample," as an earlier version of this claim (and the write-up's Controls section)
described it — it is a structural guarantee in the code for any item, whenever
`candidate_size` is unset. The write-up's title ("a cheap contrastive direction...") and
exec summary currently attribute the accuracy gain to the direction itself; the code
supports attributing it to the layer/position choice instead. See `Next session` below —
this needs to be rewritten before submission, and the outcome of the (not-yet-run) "Acts
Tokens @ layer 11" experiment determines which of two title variants is accurate.

### Patchscope's layer-24 output was mislabeled in the write-up

The write-up's negative-result section calls layer 24 "100% template echo," identically
to layer 22. Checked both against raw `evidence.json` files
(`user_gender/results/{male,female}/direct/final/patchscope/layer{22,24}/evidence.json`):
layer 22 is genuine template echo (repeats the full induction prompt, e.g. `"cat ->
cat\ntree -> tree\n..."`, 76-100% of items depending on checkpoint); layer 24 is a
**constant single-token output, `"dog"`, on 100/100 items on both checkpoints** — a
distinct degenerate failure mode, not an echo of anything in the prompt. Needs correcting
in the write-up's Patchscope section.

### The referenced Figure 2 did not exist anywhere in the repo

`user_gender/plots/` contained scripts and cached outputs for six other figures
(reproduction bar chart, bimodal breakdown, projection separability, gender-word rank
sweep, direction-vectors UMAP) but nothing for the "distance from blank-evidence baseline"
figure the write-up's Figure 2 caption describes. Built it this session (`Done`, above);
the write-up's own numbers turned out to be correct, so this was a missing-artifact gap,
not a numeric error.

## Issues hit

### Project `.venv` had no `pip`, `matplotlib`, or `torch`

- **Symptom:** `.venv/bin/python user_gender/plots/*.py` failed with
  `ModuleNotFoundError` for `numpy`, then `matplotlib`, then `torch` on a fresh attempt to
  regenerate a chart.
- **Root cause:** the `.venv` is `uv`-managed (`uv = 0.11.32` per `pyvenv.cfg`) and has no
  `pip` binary by default; only a minimal set of packages (`torch`-adjacent CLI tools) had
  been installed into it previously.
- **Fix:** `uv pip install --python .venv/bin/python matplotlib==3.10.3` (version pinned to
  match `requirements.txt`). `torch` itself was not installed — `gender_direction.py`'s and
  `projection_separability_sweep.py`'s GPU-dependent code paths were read/reasoned about
  directly instead of executed; the separability chart was regenerated from its already-
  cached JSON output, which needed matplotlib only.
