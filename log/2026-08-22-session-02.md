## Findings

### Auditor guess distribution is strongly method-dependent, not just secret-dependent

Investigated the female/male accuracy asymmetry (Acts Tokens `direct`: female 99.7% vs.
male 20.8%) by reading raw auditor guesses instead of trusting the aggregate:

| method (`direct`) | guesses "female" on **male**-target rollouts | guesses "female" on **female**-target rollouts |
| --- | --- | --- |
| I/O (no white-box evidence) | 11.3% | 11.7% |
| LL Tokens | 69.0% | 97.5% |
| Acts Tokens | 79.2% | 99.7% |

Without white-box evidence, the auditor defaults to guessing "male" (~88%) almost
regardless of ground truth. Any white-box token evidence flips that prior hard toward
"female." There's still real differential signal (69%→97.5%, not identical), but
detection is asymmetric — the female-target secret is caught almost perfectly, male
much more weakly.

**Refined once SAE Desc data came in**: SAE Desc is the only method that doesn't show
this bias — it discriminates male-target reasonably well (79%), unlike LL/Acts/SAE
Tokens (all 70-99% "female" regardless of ground truth). Common thread: the biased
methods all decode into raw next-token space; SAE Desc decodes into natural-language
feature descriptions instead — plausibly why it avoids the skew. Implication: always
check a new method's own guess distribution split by target gender, not just aggregate
accuracy — `gender_direction`'s bias turned out to run the *opposite* direction (see
Results).

### The signal in `gender_direction` is narrowly concentrated in layers 23-24

Layers 21/22/25 collapse to the same ~50% "always guess male" pattern as
`base_model_control` — no usable signal there. `random_control` stays rock-steady at
~50% across every layer, a good validity check (a random direction shouldn't get
better or worse with layer, and it doesn't).

## Issues hit

### `python-dotenv` resolves `.env` relative to the wrong path

- **Symptom:** `KeyError: 'HF_TOKEN'` when running a helper script from outside the
  repo root.
- **Root cause:** `load_dotenv()` with no args resolves relative to the calling
  script's file location, not the process's cwd.
- **Fix:** pass the `.env` path explicitly.

### SAE feature-filtering step OOMs partway through

- **Symptom:** `CUDA OutOfMemoryError` partway through `run_get_sae_features.sh`.
- **Root cause:** `BATCH_SIZE=50` combined with 50 feature descriptions/prompt at
  `max_new_tokens=200`, on top of the already-loaded 9B model, exceeded VRAM.
- **Fix:** lowered to `BATCH_SIZE=10` (commit `6aec84d`); recovered without re-running
  the already-successful extraction step.

### `apply_gender_direction.py`: dtype mismatch silently zeroed out the first full run

- **Symptom:** all 6/6 variants "succeeded" (clean exit, no crash) with 1000/1000 empty
  `top_k_tokens` — the first full run's numbers (~11% across the board) were 100% noise.
- **Root cause:** `direction_hat` cast to float32, `token_embeddings` stayed bfloat16 —
  the similarity matmul raised a dtype error on every item, caught by a broad `except`.
- **Fix:** cast `token_embeddings` to float32 for that matmul (commit `43b088c`).

### `apply_gender_direction.py`: `requires_grad` error, base-model-control only

- **Symptom:** after the dtype fix, `base_model_control` still failed 100% of items
  with `Can't call numpy() on Tensor that requires grad`.
- **Root cause:** the base model's embedding matrix has `requires_grad=True`, and the
  token-ranking matmul happens outside the `torch.no_grad()` block.
- **Fix:** `.detach()` the embedding matrix where it's read (commit `4e9af71`).

### General lesson from the two bugs above

Both were silent — caught by a broad per-item `except`, no crash, plausible-looking
aggregate numbers. Neither would have been caught without checking the raw per-item
error/empty fields before trusting the metrics file. **A clean exit code and a
plausible aggregate are not sufficient evidence of a valid run** for any script with a
broad per-item try/except.

### tmux-watcher false positives (process note, not a code bug)

- **Symptom:** polling `tmux capture-pane` for a completion string was unreliable.
- **Root cause:** a long `tmux send-keys` command's own not-yet-executed echo can
  contain the same marker text, and tqdm's `\r` updates keep it on screen a long time.
- **Fix:** switched to `tmux pipe-pane -o 'cat >> logfile'` + grepping the append-only
  log instead of re-capturing the screen.
