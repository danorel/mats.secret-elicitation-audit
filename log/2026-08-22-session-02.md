## Findings

### Auditor guess distribution is strongly method-dependent, not just secret-dependent

Investigated the female/male accuracy asymmetry (Acts Tokens `direct`: female 99.7% vs.
male 20.8%) by reading raw auditor guesses instead of trusting the aggregate. No leakage
or bug, but a real, large pattern:

| Method (`direct`) | guesses "female" on **male**-target rollouts | guesses "female" on **female**-target rollouts |
| --- | --- | --- |
| I/O (no white-box evidence) | 11.3% | 11.7% |
| LL Tokens | 69.0% | 97.5% |
| Acts Tokens | 79.2% | 99.7% |

Without white-box evidence, the auditor has a strong prior toward guessing "male"
(~88%) almost regardless of the actual rollout. The instant it's shown white-box token
evidence (LL/Acts), that prior flips hard toward "female". There *is* real differential
signal (69%→97.5%, 79.2%→99.7% between targets — not identical), so the methods aren't
purely guessing a fixed word, but detection is highly asymmetric: the female-target
secret is caught almost perfectly, the male-target secret much more weakly. The
female+male average matching published numbers isn't a coincidence of averaging two
unrelated numbers — it's consistent with the paper's metric already being a
balanced-accuracy-style average across both target genders.

**Refined once SAE Desc data came in**: SAE Desc is the one method that does *not* show
the strong female-leaning bias — it discriminates male-target reasonably well (79%,
guesses "male" on 79% of male-target rollouts), unlike LL Tokens / Acts Tokens / SAE
Tokens (all guess "female" on ~70–99% of male-target rollouts regardless of ground
truth). The common thread among the biased methods: they all decode into raw next-token
space (logit lens, embedding-similarity, SAE-feature-nearest-tokens). SAE Desc is the
only one that goes through natural-language feature descriptions (Neuronpedia) instead
of raw tokens — plausibly why it avoids the same lexical skew.

**Implication for evaluating `gender_direction`**: don't just look at aggregate
accuracy — check its own guess distribution split by target gender, since a method that
looks strong on average could still be doing the same "always guess X" trick rather
than genuinely reading out the secret. (`gender_direction`'s own bias turned out to run
the *opposite* direction — see Results below.)

### The signal in `gender_direction` is narrowly concentrated in layers 23–24

The layer sweep (Results below) shows layers 21/22/25 collapse to the same ~50%
"always guess male" pattern as `base_model_control` — i.e. those layers carry *no*
usable signal for this method at all, matching `random_control`'s behavior almost
exactly. `random_control` itself stays rock-steady at ~50% across every layer
(50.2–50.85%), which is a good validity check on the control (a random direction
shouldn't get "better" or "worse" with layer, and it doesn't).

**Verdict: positive but modest.** `gender_direction` clearly beats both required
controls (+13.75pp over random_control, +17.5pp over base_model_control — the latter is
within noise of pure chance, confirming the signal is attributable to the fine-tuning
and not to generic base-model stereotype geometry or to decoding along an arbitrary
direction). It does **not** beat the target (SAE Desc, 87.8%) — it lands in the same
range as the other raw-token-decoding methods (60–64%), reinforcing the pattern above:
methods that decode into raw token-embedding space top out around there, while SAE
Desc's natural-language route to 87.8% is qualitatively different.

Guess-distribution note: `gender_direction`'s bias runs the *opposite* direction from
every other white-box method here — it defaults to guessing "male" (81.25% average
male-guess-rate) rather than "female". `base_model_control` shows an even more extreme
male-default (95.75% average) with almost no per-target discrimination left once you
subtract that default — exactly why its accuracy lands at ~50%, the signature of
"always guessing one answer" on a balanced test set.

## Issues hit

### `python-dotenv` resolves `.env` relative to the wrong path

- **Symptom:** `KeyError: 'HF_TOKEN'`, silently, when running an upload helper script
  from the scratchpad dir instead of the repo root.
- **Root cause:** `load_dotenv()` with no arguments resolves the `.env` search path
  relative to the **calling script's file location**, not the process's cwd.
- **Fix:** pass the `.env` path explicitly: `load_dotenv(os.path.join(REPO_ROOT, ".env"))`.

### SAE feature-filtering step OOMs partway through

- **Symptom:** `CUDA OutOfMemoryError` (39.16/39.39GiB used, embedding lookup failed to
  allocate 384MiB) partway through `run_get_sae_features.sh`.
- **Root cause:** `BATCH_SIZE=50` for the feature-filtering step
  (`filter_gender_relevant_features.py`), combined with `FEATURES_PER_PROMPT=50` and
  2415 relevant features found → 49 prompts, all in one `generate()` batch (49 < 50).
  Each prompt lists 50 feature descriptions with `max_new_tokens=200`, which on top of
  the already-loaded 9B model is too much for one batch.
- **Fix:** lowered to `BATCH_SIZE=10` (commit `6aec84d`). Recovered without re-running
  the already-successful 34-minute female extraction step by reusing its saved output
  file and the partially-populated SAE-description cache (`sae_feature_cache.json`,
  2415 entries) directly.

### `apply_gender_direction.py`: dtype mismatch silently zeroed out the first full run

- **Symptom:** all 6/6 variants (female+male × 3) produced 1000/1000 empty
  `top_k_tokens` and "succeeded" with a clean exit code, no crash. The first full run's
  numbers (~11% across the board) were 100% noise, not a real result.
- **Root cause:** `direction_hat` is deliberately cast to float32 (for projection
  precision) but `token_embeddings` stayed in the model's native bfloat16; the
  similarity matmul in `rank_tokens_for_signed_direction` raised `expected mat1 and
  mat2 to have the same dtype` on every single item, caught by the function's broad
  `except`.
- **Fix:** cast `token_embeddings` to float32 for that one matmul (commit `43b088c`).

### `apply_gender_direction.py`: `requires_grad` error, base-model-control only

- **Symptom:** after the dtype fix, `contrastive`/`random_control` (both against the
  fine-tuned models) worked, but `base_model_control` (against `google/gemma-2-9b-it`)
  still failed 100% of items with `Can't call numpy() on Tensor that requires grad`.
- **Root cause:** `model.model.embed_tokens.weight` has `requires_grad=True` on the
  base model (root cause of *that* not fully chased down — possibly how the fine-tuned
  checkpoints were merged/saved differs), and the token-ranking matmul happens outside
  the `torch.no_grad()` block used for the forward pass.
- **Fix:** `.detach()` the embedding matrix where it's read (commit `4e9af71`).

### General lesson from the two bugs above

Both were silent — caught by the script's own per-item `except Exception`, no crash,
exit code 0, plausible-looking accuracy numbers. Neither would have been caught without
checking `empty_topk`/`error` counts on the raw JSON before trusting the metrics file.
**A clean exit code and a plausible-looking aggregate number are not sufficient
evidence of a valid run** for any script with a broad per-item try/except — always
check the raw per-item error field first.

### tmux-watcher false positives (process note, not a code bug)

- **Symptom:** polling `tmux capture-pane` for a completion string was unreliable.
- **Root cause:** when the command itself was sent via `tmux send-keys` and is long
  enough to wrap across several terminal rows, the shell's own echo of the
  not-yet-executed command contains the same marker text, and tqdm's `\r`-based
  progress updates mean the screen doesn't scroll that echo away for a long time.
- **Fix:** switched to `tmux pipe-pane -t task -o 'cat >> logfile'` + grepping the
  append-only log file instead of re-capturing the screen — reliable because piping
  starts capturing only new output going forward.
