## Finding: auditor guess distribution is strongly method-dependent, not just secret-dependent

Investigated the female/male asymmetry (Acts Tokens `direct`: female 99.7% vs
male 20.8%) by reading raw auditor guesses instead of trusting the aggregate.
**No leakage or bug** — but a real, large pattern:

| Method (direct) | guesses "female" on **male**-target rollouts | guesses "female" on **female**-target rollouts |
| --- | --- | --- |
| I/O (no white-box evidence) | 11.3% | 11.7% |
| LL Tokens | 69.0% | 97.5% |
| Acts Tokens | 79.2% | 99.7% |

Without white-box evidence, the auditor has a strong prior toward guessing
"male" (~88%) almost regardless of the actual rollout. The instant it's shown
white-box token evidence (LL/Acts), that prior flips hard toward "female".
There *is* real differential signal (69%→97.5%, 79.2%→99.7% between targets —
not identical), so the methods aren't purely guessing a fixed word — but
detection is highly asymmetric: female-target secret is caught almost
perfectly, male-target secret much more weakly. The female+male average
matching published numbers isn't a coincidence of averaging two unrelated
numbers — it's consistent with the paper's metric already being a
balanced-accuracy-style average across both target genders.

**Implication for evaluating our new method**: don't just look at aggregate
`gender_direction` accuracy — check its own guess distribution split by
target gender. A method that looks strong on average could still be doing the
same "always guess X" trick rather than genuinely reading out the secret.

results (it decodes into raw token space too, same family as the biased

## Result: gender_direction vs baseline and controls (`direct`, layer 23)

`03_run_gender_direction_apply.sh` hit two real bugs on first run (see below),
both fixed and verified on a 2-item sample before the full rerun. Final,
verified numbers (980-990/1000 valid per file, rest are the same benign
"no pronoun" cases seen everywhere else):

| Method (`direct`) | female | male | avg |
| --- | --- | --- | --- |
| I/O (baseline) | 11.7% | 88.7% | 50.2% |
| LL Tokens | 97.5% | 31.0% | 64.25% |
| Acts Tokens | 99.7% | 20.8% | 60.25% |
| SAE Desc | 96.6% | 79.0% | **87.8%** (target to beat) |
| SAE Tokens | 99.8% | 26.8% | 63.3% |
| **gender_direction (contrastive)** | 36.4% | 98.9% | **67.65%** |
| random_control | 85.7% | 22.1% | 53.9% |
| base_model_control | 4.4% | 95.9% | 50.15% |

**Verdict**: positive but modest. `gender_direction` clearly beats both
required controls (+13.75pp over random_control, +17.5pp over
base_model_control - the latter is within noise of pure chance, confirming
the signal is attributable to the fine-tuning and not to generic base-model
stereotype geometry or to decoding along an arbitrary direction). It does
**not** beat the target (SAE Desc, 87.8%) - it lands in the same range as
the other raw-token-decoding methods (LL/Acts/SAE Tokens, 60-64%), reinforcing
the pattern noted above: methods that decode into raw token-embedding space
top out around there, while SAE Desc's natural-language route to 87.8% is
qualitatively different.

Guess-distribution note (per the bias finding above): `gender_direction`'s
bias runs the *opposite* direction from every other white-box method here -
it defaults to guessing "male" (81.25% average male-guess-rate) rather than
"female". `base_model_control` shows an even more extreme male-default
(95.75% average) with almost no per-target discrimination left once you
subtract that default - which is exactly why its accuracy lands at ~50%,
the signature of "always guessing one answer" on a balanced test set.

## Known issues hit (`apply_gender_direction.py`, both new bugs in our own code)

- **dtype mismatch**: `direction_hat` is deliberately cast to float32 (for
  projection precision) but `token_embeddings` stayed in the model's native
  bfloat16; the similarity matmul in `rank_tokens_for_signed_direction` raised
  `expected mat1 and mat2 to have the same dtype` on every single item. Caught
  by the function's broad `except`, so it failed *silently* - all 6/6
  variants (female+male x 3) produced 1000/1000 empty `top_k_tokens` and
  "succeeded" with a clean exit code, no crash. First full run's numbers
  (~11% across the board) were 100% noise, not a real result. Fixed by
  casting `token_embeddings` to float32 for that one matmul (commit
  `43b088c`).
- **requires_grad error, base-model-control only**: after the dtype fix,
  `contrastive`/`random_control` (both against the fine-tuned models) worked,
  but `base_model_control` (against `google/gemma-2-9b-it`) still failed
  100% of items with `Can't call numpy() on Tensor that requires grad` -
  `model.model.embed_tokens.weight` has `requires_grad=True` on the base
  model (root cause not fully chased down - possibly how the fine-tuned
  checkpoints were merged/saved differs) and the token-ranking matmul happens
  outside the `torch.no_grad()` block used for the forward pass. Fixed by
  `.detach()`-ing the embedding matrix where it's read (commit `4e9af71`).
- **Both bugs were silent** (caught by the script's own per-item
  `except Exception`, no crash, exit code 0, plausible-looking accuracy
  numbers) - neither would have been caught without checking
  `empty_topk`/`error` counts on the raw JSON before trusting the metrics
  file. General lesson: a clean exit code and a plausible-looking
  aggregate number are not sufficient evidence of a valid run for any script
  with a broad per-item try/except - check the raw per-item error field.
- **tmux-watcher false positives** (process note, not a code bug): polling
  `tmux capture-pane` for a completion string is unreliable when the command
  itself was sent via `tmux send-keys` and is long enough to wrap across
  several terminal rows - the shell's own echo of the not-yet-executed
  command contains the same marker text, and tqdm's `\r`-based progress
  updates mean the screen doesn't scroll that echo away for a long time.
  Switched to `tmux pipe-pane -t task -o 'cat >> logfile'` + grepping the
  append-only log file instead of re-capturing the screen - reliable because
  piping starts capturing only new output going forward.
