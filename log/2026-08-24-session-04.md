## Summary

## Findings

### The pre-fix collapse is confirmed on a controlled sample, not just the session-3 spot-check

Pulled the existing (pre-fix) `layer10_contrastive` female apply output's first 30
items and compared to a fresh 30-item pilot run through the fixed code, on the *same*
input file in the *same* order (verified via the apply file's `source_data_file`
metadata match). **Before: 1 unique top-5 token combo across all 30 items** (`
businesswoman, 小姐, рада, Woman, WTA` - literally byte-identical for every item).
**After: 3 unique top-5 combos (9 unique top-20 combos) across the same 30 items** -
confirms the fix makes the decode genuinely per-item-dependent, where before it was a
deterministic function of one sign bit.

### The fixed (plain) decode is dominated by pronoun surface form, not gender content

Reading the fixed pilot's actual token lists: female-target item 0's top tokens are
`me, Me, me, I, <strong>, ME, e, PLEASE, My, [, ...` - the literal pronoun token at that
position and its case/language variants, not gender-coded vocabulary. Grouping items by
top-20 combo shows clusters track **which pronoun word was used** ("me" vs "my" vs
"our"), not gender. Consistent with layer 10 being shallow enough that the residual
stream is still dominated by the position's own token identity (same pattern as
session 3's Patchscope finding at early-to-mid layers). The raw projection-sign signal
(990/990 zero-overlap separability, session 3) is untouched by this - only the
nearest-token *decode* fails to surface it at this layer.

### Once decode targets the real residual, `direction` becomes structurally irrelevant to the output

With the sign-only-lookup bug fixed, `top_k_tokens` depends only on the real per-item
residual - `direction` is used solely to compute the diagnostic `mean_projection` field,
which the auditor never reads. Verified empirically: `contrastive` and `random_control`
apply outputs are byte-identical at 100/100 items. Consequence: post-fix,
`gender_direction` is not a distinct method from the paper's own Acts Tokens applied at
layer 10 - `direction` plays no causal role in what the auditor sees. This is a genuine
negative finding for Hypothesis D as originally framed (a nearest-token decode of a
*direction vector* is mathematically incapable of being both per-item-varying and
direction-specific at the same time - see Issues hit).

### Blend decode passes three independent legitimacy stress tests

Prompted by direct user pushback ("is this another hack?"). Restricting the candidate
vocabulary to the `candidate_size` tokens nearest `direction` (signed by the item's own
projection), then ranking *those* by the real residual:

1. **No label leakage** - grepped the full data-loading path; only `user_prompt` and
   `model_response` are ever read from the data file, no ground-truth field.
2. **Content was already there** - `Women`/` women` are present in the *unrestricted*
   plain decode's top-200 list at rank 135/147, just buried below pronoun noise. Blend
   decode filters, it doesn't invent.
3. **Genuine per-item work, not a disguised static lookup** - the "static" ranking
   (nearest tokens to `direction` alone, zero residual involvement) is **literally
   identical to the original pre-fix bug's output** (`businesswoman, 小姐, рада, Woman,
   WTA...`). Real per-item blend output overlaps with this static list only ~45-50%
   (not ~95-100%, which would indicate the residual isn't doing real work).

Also confirmed: the direction correctly flips sign and vocabulary between the female
model (`mean_proj` +2 to +11, tokens `Women/woman/WOMEN/mujer/Frauen`) and the male model
(`mean_proj` -41 to -10, tokens `Man/Men/male/masculino/erkek/Männer`).

### `random_control`'s elevated average is a real, quantifiable auditor-bias artifact - but not fully explained

At candidate_size=500 (n=300), `random_control` averaged 58.83%, not ~50% like every
other validated null in this project (layer23/layer24 `base_model_control`: 50.15%/
50.25%; this session's own blend `base_model_control`: 49.66%). Root-caused the
mechanism: the auditor has a known bias (session 2) toward guessing "female" given *any*
raw-token-list evidence, but the bias's *magnitude* differs by checkpoint - 78.33%
"female" guesses on the female-model file vs. 60.67% on the male-model file. If the bias
probability were identical across files, the average would land exactly at 50%
regardless of its size; since it isn't identical, the average is skewed. Ruled out a
generic "checkpoint style" explanation: the `io` baseline (auditor reads only the
response text, no token evidence at all) shows a negligible 0.4pp gap between files,
while Acts Tokens (a real, informative decode) shows a comparable-magnitude 20.5pp gap -
so the effect is specific to decoding the residual stream at all (real or random
direction), not a general text-style artifact.

### The candidate_size deviation is non-monotonic, ruling out "just widen the pool" as a clean fix

| candidate_size | contrastive avg | random_control female | random_control male | random_control avg |
| --- | --- | --- | --- | --- |
| 500 (n=300) | 96.67% | 78.33% | 39.33% | 58.83% |
| 2000 (n=100) | 100.00% | 92.00% | 19.00% | 55.50% |
| 5000 (n=100) | 100.00% | 88.00% | 62.00% | 75.00% |

`random_control` does not converge toward chance as candidate_size grows - it gets
*worse* at 5000 than at 2000. `contrastive` climbing to a ceiling of 100% at n=100 is
itself flagged as possibly a small-sample ceiling effect, not necessarily a real 100% at
full scale.

### Multi-seed test: neither clean noise nor a clean systematic bias - verdict is that blend decode is falsified

Pre-committed decision rule (agreed with user before running, to avoid post-hoc
interpretation): seeds scattering widely and non-directionally around 50% → single-draw
noise, blend decode simply can't produce a clean control at this candidate_size; seeds
clustering consistently above ~55-58% → real systematic bias needing deeper work.

5 independent random unit vectors, candidate_size=2000, n=100 each, both genders:

| seed | female | male | avg |
| --- | --- | --- | --- |
| 1 | 46% | 94% | 70.00% |
| 2 | 100% | 5% | 52.50% |
| 3 | 67% | 47% | 57.00% |
| 4 | 70% | 30% | 50.00% |
| 5 | 100% | 14% | 57.00% |

Mean 57.3%, stdev 7.71pp, range 50.00%-70.00%, **0/5 seeds below 50%**. Under a fair
coin, 0/5 below 50% has ~3% one-tailed probability - suggestive of a real one-directional
effect, not pure symmetric noise. But the range (50-70%) and especially the wild swing in
individual female/male numbers per seed (5% to 100%) are too unstable to call this a
clean, reliable systematic bias either. **This is the worst possible outcome for the
method**: not clean enough to trust as signal, not random enough to dismiss and average
away. Combined with the non-monotonic candidate_size sweep (previous section), the
conclusion is that no candidate_size tested makes `random_control` a valid null -
**blend decode is falsified as a method**, not merely unproven. Closed as a line of
investigation; see Decisions/Next session for the pivot.

### Correction: the auditor sees the top-200 tokens, not top-5 - reopens layer 11

`format_token_info`'s bare Python default is `num_tokens=5`, but
`run_auditor_residual_tokens.sh` (the wrapper used for every audit run in this project,
including every one this session) hardcodes `NUM_TOKENS=200`, confirmed both by
grep and by directly observing real 200-token prompts in this session's own captured
tool output. This raises the real "would the auditor ever see this" threshold from
rank ≤5 to rank ≤200. Under that corrected threshold, layers 9-18 have MALE median
rank ≤200 essentially throughout, and several female layers (11, 14, 17, 19-21, 23)
qualify too - reopening layer 11 (rank 66/159) as a real, worth-testing candidate
rather than dismissing the whole plain-decode line. Provenance-checked afterward: both
`TOP_K=200` (extraction) and `NUM_TOKENS=200` (auditor) were already present at the
upstream fork point (commit `45aae57`, `run_get_logit_lens.sh` /
`run_auditor_logit_lens.sh`) - the paper authors' own choice, undocumented but not
something this project introduced or changed, so the correction restores parity with
the paper's actual methodology rather than deviating from it.

### Layer 11's 68.34% average hides a bimodal, male-side-only effect - real effective n is 60, not 290

The 10 response-variants per unique prompt are not independent observations: pronoun
positions live in the user prompt, strictly before `<start_of_turn>model` in the token
sequence, so by causal masking the captured activation cannot depend on which response
followed (same mechanism already noted for the paper's own methodology in session 3).
Real effective sample size is **60** - 30 unique prompt phrasings × 2 checkpoints
(female-model and male-model are different fine-tunes, so the same phrasing through
each is a genuinely independent observation) - not 290 raw items and not 30.

Breaking the 60 units down by accuracy is not a smooth spread - it's concentrated
almost entirely on one side:

| accuracy bucket | count | composition |
| --- | --- | --- |
| 0.00 | 14 | all male |
| 0.01-0.49 | 4 | all male |
| 0.50-0.89 | 3 | all male |
| 0.90-1.00 | 39 | 29 female @1.00 + 1 female @0.90 + 9 male |

**Female is flat at ceiling** (29/30 phrasings exactly 1.00, one at 0.90) - saturated
by the same "auditor defaults to female" bias documented since session 2, showing no
real per-prompt variation. **All the bimodality is on the male side**: 14/30 phrasings
fail completely, ~9/30 succeed completely, the rest scatter in between - real signal
that only overcomes the bias for some ways of phrasing the direct question, not a
uniform per-conversation read. Not a new bug - a consequence of the same
pronoun-position/causal-masking design shared with the paper's own methods - but the
honest headline is "9-10 of 30 direct-question phrasings read reliably on the male
side, 14 never do" rather than a single smoothed-over 68.34%.

### External review found a real blocker: 68.34% wasn't apples-to-apples with the n=1000 baseline table - now resolved

A critique pass (external review, this session) flagged that the 68.34% headline used
`--limit 300`, and `apply_gender_direction.py`'s `--limit` is `input_output_pairs[:args.limit]`
- a **positional slice of the first 300/1000 items** (the first 30 of 100 unique
prompts, not a random sample), while every number in the reproduction table above (io,
Acts Tokens, SAE Desc) uses the full n=990/1000. Comparing "beats Acts Tokens by ~8pp"
across a 30-prompt subset and a 100-prompt full set was not a valid comparison as
originally stated, independent of whether the subset happened to be representative.

**Resolution:** reran layer 11 (`contrastive` + `base_model_control`, both genders, no
`--limit`) at the full n=1000. Numbers land at 68.55%/50.35% avg - within 0.2-0.35pp of
the original n=300 read (68.34%/50.00%) - see the updated Results table above. The
n=300 slice was not cherry-picked or unrepresentative; the blocker was a real
comparability gap, not a real inflation, and it's now closed by using n=1000
everywhere the reproduction table is cited.

The same review pass also flagged two lower-priority items, both left as documentation
rather than code changes: (a) `batch_inference.py`'s `"strategy": "standard"` metadata
field names the *sampling* strategy (standard/prefill/multi_turn_jailbreak/
user_persona), not which *prompt set* (`standard` vs `direct`) was used - a genuine
naming collision in the paper's own upstream harness, not a bug this project
introduced, so it's noted here rather than "fixed" in code; (b) the auditor's guess-bias
("no evidence → guess male ~88%; any raw-token evidence → guess female 70-99%; SAE
Desc's natural-language decode is the only method without this skew") is a
method-*format*-specific artifact of the auditor's own prior, not a secret-specific
finding - worth stating explicitly in any writeup that leans on female-side accuracy as
evidence of signal, since a chunk of that number is the auditor's own bias, not the
extraction method.

### Code audit before finalizing: one real bug found (a citation error, not a broken

### Closing mechanistic synthesis: why gender_direction never decodes, across three independent lines of evidence

Per direct user request for the "why," not just "didn't work" (matching CLAUDE.md's
own standard for a negative result). Three independently-collected findings converge:

1. **This session's nearest-token rank sweep** (all layers 0-24): the best-matching
   gender word's full-vocabulary rank is 60-400 at every layer that isn't outright
   broken - never top-10, never close to how a real token's own embedding would rank
   against itself.
2. **This session's Patchscope sweep** (layers 8-32, both templates, both fine-tuned
   checkpoints, scale 0.3x-20x): real word embeddings decode cleanly in a genuine
   working window (16-20); `gender_direction` never produces gender content anywhere
   in that space, converging on silence or generic continuation instead.
3. **Session 3's UMAP/PCA on raw contrastive-pair activations**: points cluster by
   sentence *topic*, not by gender - the gender axis is not a natural, separate
   cluster in activation space; it only exists as the *difference* extracted by
   paired subtraction across topically-diverse sentences.

**The most likely explanation, consistent with all three**: `gender_direction` is a
diff-of-means vector (`mean(female_acts) - mean(male_acts)` over 51 topically-varied
contrastive pairs, scaled to natural residual norm afterward) - a real, structurally-
verified fact about how it's built (`build_gender_direction.py`). It carries genuine
linearly-separable classification signal (the raw projection-sign finding, session 3:
990/990 zero-overlap separability), but it was never a point the model learned to
treat as a single nameable concept - not a real token embedding, not an SAE decoder
direction, not anything the model has processed as actual input. Both decode routes
tried this session look for exactly that kind of "known point": nearest-token lookup
asks "which vocabulary token is this closest to" (answer: nothing very close - rank
60-400), and induction-based Patchscope relies on induction heads recognizing "this
looks like a token I've seen before in context" (answer: nothing recognizable enough
to latch onto - silence, or an arbitrary generic continuation). The one honest caveat
on the induction-head account specifically: it's a well-motivated interpretation
consistent with every observation here, not something directly confirmed via
attention-pattern inspection - stated as the best available explanation, not a proven
mechanism.

## Issues hit

### `top_k_tokens` decoded the static `gender_direction` vector instead of the per-item residual

- **Symptom:** flagged in session 3's post-session review - every item's "evidence" was
  one of exactly 2 fixed token lists (990/1000 items at layer 10, same at layer 23),
  chosen by a single upstream sign bit, not real per-item activation content.
- **Root cause:** `apply_gender_direction.py`'s old `process_pair` used the per-item
  residual only to compute the sign of `mean_proj` (residual · direction), then called
  `rank_tokens_for_signed_direction(±direction_hat, ...)` - ranking vocabulary tokens
  against the *direction vector itself* (sign-flipped), not against the residual. Since
  cosine-similarity ranking against a fixed query vector is invariant to positive
  scaling and only flips wholesale on sign, this is mathematically guaranteed to produce
  at most 2 distinct rankings regardless of how the per-item activation actually varies.
- **Fix:** decode target changed to the actual per-item `residual_reps` at each pronoun
  position, combined across positions via the same `get_combined_top_k_tokens_pronouns`
  helper `residual_tokens.py`'s Acts Tokens method already uses. `direction` is now used
  only for the diagnostic `pronoun_projections`/`mean_projection` fields, not decoding.
  Verified via the before/after pilot above.

### The fix's own consequence: any single fixed vector's nearest-token decode can't be both per-item-varying and vector-specific

Not a code bug - a structural/mathematical property. Ranking vocabulary by cosine
similarity to a *single fixed query vector* is invariant to positive scaling of that
vector and can only flip discretely on sign - so decoding `direction` itself is
mathematically capped at 2 possible outputs (the original bug). Decoding the real
residual instead fixes the per-item-variation problem but removes `direction` from the
computation entirely (the new finding this session). Blend decode (candidate-set
restriction) is the current attempt to have both properties at once; whether it
succeeds cleanly is still open (see Findings/Results).
